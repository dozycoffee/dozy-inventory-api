# ADR-0020: 가용 재고 조회 규칙

## 상태

Accepted (2026-10-08)

## 배경 (Context)

F-009에서 재고 조회를 만든다. 조회는 채널용 가용 재고(OMS·가맹점), 관리자용 현황·상세, 이력으로 나뉘고 호출하는 주체와 요구가 달라 단계별로 나눠 진행한다. 1단계는 채널용 가용 재고 조회이며 영속성·application 계층(이 ADR)과 웹 어댑터(다음 PR)로 계층별 PR을 나눈다.

## 결정 (Decision)

1. **조회는 `productIds`(필수, 최대 100개)와 `warehouseIds`(선택, 최대 100개)로 한다.** 가맹점이 근처 창고를 몰라도 되도록 최적 창고를 고르는 일은 호출 서비스(OMS·Store)가 맡고(가맹점 위치와 배송 정책은 그쪽 데이터), inventory는 창고별 가용 수량을 주고 지정한 창고에서 예약한다. 창고를 생략하면 모든 창고를 보여 줘 멀리 있는 창고의 재고도 호출 서비스가 볼 수 있다. 점주에게 어느 창고까지 보여 줄지는 Store가 정한다.
2. **응답은 상품별로 묶고 창고별 수량과 합계를 준다.** 창고를 지정하면 지정한 모든 창고가 나오고(재고 행이 없으면 0), 지정하지 않으면 그 상품의 재고 행이 있는 창고가 나온다(가용 0인 창고 포함). 재고가 없는 상품도 합계 0으로 나온다. 합계는 `Long`이다.
3. **가용 수량은 `NORMAL` 품질이고 할당 보류가 아닌 행의 (총 수량 − 예약 수량) 합이다.** 한 문장의 집계 SQL로 구하고, 도메인 모델(`Inventory.isAllocatable`, `availableQuantity`)과 같은 규칙인지 상태 조합 전체에서 비교하는 테스트를 둔다.
4. **전체 창고 × 전체 상품을 조회하는 채널용 API는 두지 않는다.** 채널은 필요한 상품을 이미 알고(Catalog), 전체 집계는 부하가 크며 조회 결과를 약속으로 오해할 위험이 있다. 전체 목록은 관리자 재고 현황(4.2)이 맡는다. 캐시 도입 시점은 계속 미확정이다.
5. **호출 권한은 `inventory:service`와 `inventory:admin`이다.** 창고 관리자는 배정된 창고만 볼 수 있어야 하므로 창고 접근 제어(F-021) 이후에 연다.
6. **상품이 IMS에 있는지는 확인하지 않는다.** 모르는 상품은 합계 0으로 응답해 조회를 가볍게 유지한다.
7. **창고 없이 상품으로 조회하는 경로를 위해 `inventory (product_id, warehouse_id)` 인덱스를 추가한다**(V4). 기존 `idx_inventory_available`은 `warehouse_id`가 앞이라 상품만으로는 쓸 수 없다.

## 결과 (Consequences)

- 얻는 것: 가맹점이 창고를 몰라도 되는 흐름을 호출 서비스가 구성할 수 있고, 창고별 수량과 합계로 단일·복수·전체 창고 조회를 모두 한 계약으로 처리한다. 가용 계산이 모델과 어긋나지 않는다.
- 감수하는 것: 호출 서비스가 최적 창고 선택 로직을 가져야 한다. 창고 생략 시 재고 행이 있는 창고만 나오므로 "재고가 한 번도 없던 창고"는 보이지 않는다. 100개를 넘는 상품은 여러 번 나눠 호출해야 한다. 인덱스가 하나 늘어 쓰기 비용이 조금 늘어난다.
