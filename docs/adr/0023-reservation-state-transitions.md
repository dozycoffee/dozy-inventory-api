# ADR-0023: 예약 상태 전이(확정·해제·연장·만료) 규칙

## 상태

Accepted (2026-10-08). 구현은 계층별 PR로 나눈다: (1) inventory의 예약 수량 해제 UseCase와 reservation 도메인의 상태 전이·영속성, (2) 확정·해제·연장·만료 application, (3) 웹 어댑터와 만료 스케줄러.

## 배경 (Context)

F-010에서 예약을 만들 수 있게 되었지만 이후 전이가 없어, 한 번 잡은 수량이 풀리지 않고 WMS 출고 지시로 이어지지도 않는다. 시나리오가 정한 것은 확정 전 예약만 만료되고(결정 2), 연장은 총 수명 상한 안에서만 되며, 만료된 `RESERVED`는 강제 해제하고 `CONFIRMED`는 건드리지 않는다는 것(결정 6)이다. 전이별 입력, 멱등 방식, 동시성, 호출 주체가 남았다.

## 결정 (Decision)

1. **상태 전이**

   ```
   RESERVED ──확정──▶ CONFIRMED ──(출고 확정, F-012)──▶ FULFILLED
      │ │                │
      │ └──연장(상한 이내)  └──해제(WMS 취소 확정 후)──▶ RELEASED
      ├──해제──▶ RELEASED
      └──만료(스캔)──▶ EXPIRED
   ```

2. **확정**: `RESERVED` → `CONFIRMED`. 만료 시각이 사라지고 확정 시각이 남는다. 만료 시각이 지난 예약은 확정할 수 없다(`INV_RESERVATION_EXPIRED`, 409). 아직 스캔이 해제하지 않았어도 만료된 예약은 약속이 아니다. 확정은 WMS 출고 지시를 위한 이벤트를 낸다.
3. **해제**: `RESERVED`와 `CONFIRMED` 모두 `RELEASED`로 바꾸고 예약 수량을 가용 수량으로 되돌린다. 이미 `RELEASED`·`EXPIRED`이면 바꾸지 않고 현재 상태를 반환한다. `FULFILLED`는 해제할 수 없다(`INV_INVALID_RESERVATION_STATE`, 409. 출고 완료 후는 반품 흐름).
4. **연장**: 확정 전 예약의 만료 시각을 **새 만료 시각(절대값)**으로 바꾼다. 생성과 같은 형식이다. 현재 만료 시각 이상이고 최대 만료 시각(생성 시각 + 채널 상한) 이하이며 현재 이후여야 한다(어기면 400 `INV_INVALID_RESERVATION_EXPIRY`). 같은 시각이면 바뀌지 않는다. 만료된 예약은 연장할 수 없다(409 `INV_RESERVATION_EXPIRED`). 확정 전이 아니면 409(`INV_INVALID_RESERVATION_STATE`)이다.
5. **만료**: 만료 시각이 현재 이하인 `RESERVED`를 `EXPIRED`로 바꾸고 예약 수량을 되돌린다. 만료 시각은 만료된 시각으로 남긴다. 스케줄러가 고정 간격으로 만료 대상을 한 번에 일정 개수씩 가져와 예약마다 별도 트랜잭션으로 처리한다(한 건의 실패가 나머지를 막지 않는다).
6. **멱등은 상태 기반이다.** 확정·해제·연장은 예약 ID가 대상을 식별하므로 `Idempotency-Key` 없이 상태로 멱등하게 만든다: 이미 목표 상태이면 아무것도 바꾸지 않고 200으로 현재 상태를 반환하고, 불가능한 전이는 409이다. 예약 생성은 새 리소스를 만드는 요청이라 멱등 키를 쓴다(ADR-0022).
7. **동시성은 조건부 UPDATE로 판정한다.** 상태·만료 시각·확정 시각 갱신은 `WHERE status = :읽은 상태`로 실행해 영향 행이 0이면 그 사이 다른 요청이 상태를 바꾼 것이다. 진 쪽은 새로 읽어 결과를 판정한다(이미 목표 상태면 성공, 아니면 409). 같은 예약을 동시에 확정해도 정확히 한 쪽만 상태를 바꾼다.
8. **수량 복원은 inventory의 UseCase로 한다.** 해제와 만료는 `ReleaseInventoryUseCase`로 재고 행별 예약 수량을 되돌린다. 예약 상태 변경, 수량 복원, 이력, 이벤트는 한 트랜잭션이다. 여러 행은 `inventory_id` 오름차순으로 갱신해 데드락을 피한다. 예약과 해제는 총 수량을 바꾸지 않으므로 `inventory_history`에 기록하지 않고 `reservation_event`(`CONFIRMED`, `RELEASED`, `EXTENDED`, `EXPIRED`)에 남긴다.
9. **호출은 `inventory:service`만 허용한다.** OMS·Store·WMS는 모두 system client이고 본사 관리자가 수동으로 확정·해제하는 경로는 두지 않는다(원칙 6). 잘못 남은 예약을 사람이 풀어야 하는 요구가 생기면 그때 추가한다.
10. **이벤트는 발행 포트와 로그 구현이다**(ADR-0022 결정 13과 같은 방식). 예약 변경 이벤트(`CREATED`, `CONFIRMED`, `EXTENDED`, `RELEASED`, `EXPIRED`)는 상품별 수량과 재고 행별 할당 내역(재고 행 ID, 수량)을 담는다. WMS가 출고를 지시하려면 Lot 번호·유통기한 같은 Lot 정보가 필요한데, 이벤트 계약(페이로드, 파티션 키)은 F-018에서 Outbox와 함께 정하며 그때 inventory 쪽 조회로 Lot 정보를 채운다. 실제 발행도 그때 Outbox로 교체한다.
11. **트랜잭션 안의 잠금 순서**: 예약 상태 변경(예약 행 잠금) 뒤에 재고 행을 `inventory_id` 오름차순으로 갱신한다. 예약 생성은 재고 행을 잠근 뒤 새 예약 행을 INSERT할 뿐 기존 예약 행을 건드리지 않으므로 두 경로가 서로를 기다리는 순환이 생기지 않는다.

## 결과 (Consequences)

- 얻는 것: 예약 수량이 반드시 풀리고(해제·만료), 동시 요청에서도 상태가 한 번만 바뀌며, 재전송에 안전하다(상태 기반 멱등). 멱등 키 저장소 없이 단순하다.
- 감수하는 것: 같은 예약 ID에 대한 확정·해제가 순서가 뒤바뀌어 도착하면 먼저 도착한 것이 이긴다(호출 서비스가 순서를 관리해야 한다). 만료 스캔 간격만큼 만료된 예약의 수량이 늦게 풀린다(그 사이에도 확정·연장은 막는다). 확정 이벤트는 F-018 전까지 실제로 발행되지 않는다.
