# ADR-0029: 반품 복귀 반영 규칙

## 상태

Accepted (2026-10-13). 입고 확정(ADR-0017, ADR-0019)과 폐기 확정(ADR-0028)을 따르고, 시나리오 7.1 원문이 Notion에만 있어 이 ADR에서 정하지 않은 값은 그 선례를 따랐다.

## 배경 (Context)

출고된 물건이 반품되면 WMS가 검수해 정상·불량을 판정하고 inventory 서비스에 재고 복귀를 알린다. 반품 복귀는 입고와 효과(재고 증가)는 같지만 이력을 `RETURN`으로 분리해 기록한다(시나리오 결정 9). inventory 서비스는 출고 이후의 재고를 추적하지 않으므로(ADR-0007) 반품은 출고와 연결하지 않고 새로 들어온 재고로 다룬다.

## 결정 (Decision)

1. **요청 한 건은 반품 품목 한 줄이다.** 멱등 키는 품목마다 하나이고 원인 문서는 WMS의 반품 상품 ID(`returnItemId`)다. 원래 출고(예약)와는 연결하지 않는다.
2. **이미 등록된 Lot의 반품만 받는다.** `상품 + Lot 번호`로 Lot을 찾고 없으면 404(`INV_LOT_NOT_FOUND`)로 거부한다(사용자 확인). 입고와 달리 Lot을 새로 만들지 않고 제조일자·유통기한도 받지 않는다. 잘못된 Lot 번호가 재고로 들어오는 것을 막는다. 상품이 없으면 404(`INV_PRODUCT_NOT_FOUND`)이고 비활성 상품도 이미 돌아온 물건이므로 반영한다.
3. **품질 상태는 WMS 검수 판정인 `NORMAL`·`DEFECTIVE`만 받는다.** 폐기 예정은 400(`INV_INVALID_RETURN_QUALITY_STATUS`)이다(폐기 예정은 유통기한 스캔이 정한다). 판정에 맞는 품질 상태의 행에 더하고 행이 없으면 만든다. 반품된 Lot이 이미 경과했으면 정상 행에 들어가고 다음 유통기한 스캔이 폐기 예정으로 옮긴다.
4. **이력은 `RETURN`, 원인 문서는 `RETURN_ITEM`이다.** 수량·이력·이벤트는 한 트랜잭션이고 이벤트는 재고 증가(`INVENTORY_INCREASED`)다.
5. **재요청은 처음 응답과 같은 결과를 준다.** 저장된 이력으로 결과를 다시 만들고(처음 시점의 `quantityAfter`), 내용이 다르면 409(`INV_IDEMPOTENCY_KEY_CONFLICT`)다. 같은 키가 동시에 들어오면 늦은 쪽의 이력 저장이 중복 키로 실패해 롤백되고(증가도 되돌아간다) 먼저 처리된 결과를 받는다.
6. **API는 `POST /api/v1/returns`이고 호출은 `inventory:service`만 허용한다.** 멱등 키는 `Idempotency-Key` 헤더이고 본문은 `warehouseId`, `productId`, `lotNumber`, `qualityStatus`, `quantity`, `returnItemId`이다. 처음 반영과 재요청 모두 200이고 응답은 입고와 같은 모양이다.

## 결과 (Consequences)

- 얻는 것: 반품이 입고와 구분되는 이력으로 남고 WMS 재전송에 안전하다. 출고와 연결하지 않아 모델이 단순하다.
- 감수하는 것: 등록되지 않은 Lot(예: 이관 전 출고분)의 반품은 받지 못해 먼저 입고 경로로 Lot을 등록해야 한다. 반품이 품목 단위 호출이라 반품 건에 품목이 많으면 호출 수가 늘고 건 전체가 원자적이지 않다.
