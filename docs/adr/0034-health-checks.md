# ADR-0034: 헬스 체크와 graceful shutdown

## 상태

Accepted (2026-10-12). 배포 플랫폼(Kubernetes 등)이 아직 정해지지 않아 플랫폼에 중립인 범위만 정한다. 메트릭, 구조화 로그, 알림 기준은 서비스 간 규약과 부하 테스트 시점에 함께 정하려고 미뤘다.

## 배경 (Context)

컨테이너 플랫폼과 로드밸런서는 인스턴스가 살아 있는지, 요청을 받을 준비가 됐는지를 HTTP 헬스 체크로 판단한다. 이게 없으면 기동 중에 트래픽이 들어오고, 죽은 인스턴스가 재시작되지 않고, 롤링 배포가 무중단이 되지 않는다. 헬스 엔드포인트는 Spring Boot actuator의 기본 경로를 쓰므로 어느 플랫폼에서도 같다.

## 결정 (Decision)

1. **actuator는 `health`만 노출한다.** 메트릭, 환경, 빈 정보 같은 다른 엔드포인트는 노출하지 않는다(관측성 작업에서 별도로 정한다). 응답에 상세 정보를 싣지 않고 상태(`UP`/`DOWN`)만 준다.
2. **liveness(`/actuator/health/liveness`)는 프로세스 상태만 본다.** DB나 Kafka가 죽었다고 인스턴스를 재시작하면 장애가 커지므로 외부 의존성을 넣지 않는다.
3. **readiness(`/actuator/health/readiness`)는 DB(R2DBC)를 포함하고 Kafka는 제외한다.** DB가 없으면 조회·예약을 처리할 수 없다. 브로커가 죽어도 변경은 Outbox에 쌓이고 복구되면 발행되므로(원칙 8, ADR-0025) 요청 처리에는 영향이 없다.
4. **헬스 경로는 인증 없이 호출할 수 있다**(`dozy.auth.public-paths`에 `/actuator/health`, `/actuator/health/**`). 플랫폼의 probe는 토큰이 없다. 다른 경로는 보안 체인이 그대로 막는다(토큰이 없으면 401, 노출하지 않은 엔드포인트는 404). 관리 포트는 분리하지 않는다. 노출이 헬스뿐이고 응답이 상태뿐이라 같은 포트로 충분하다.
5. **graceful shutdown을 켠다**(`server.shutdown=graceful`, 대기 최대 30초). 종료 신호를 받으면 readiness가 실패해 새 트래픽이 끊기고 진행 중인 요청이 끝나길 기다린 뒤 종료한다. 스케줄러와 Outbox 발행은 at-least-once와 조건부 갱신이라 중간에 끊겨도 안전하다.

## 결과 (Consequences)

- 얻는 것: 어느 배포 환경에서도 같은 헬스 경로로 기동 대기, 재시작, 롤링 배포를 설정할 수 있다. 종료 시 요청이 끊기지 않는다.
- 감수하는 것: 헬스 경로가 인증 없이 열려 있다(상태 문자열만 노출). 외부 의존성(Kafka, WMS) 장애는 헬스로 드러나지 않으므로 메트릭과 알림이 필요하다(미룬 관측성 작업). 종료 대기 시간이 플랫폼의 종료 유예 시간(예: Kubernetes `terminationGracePeriodSeconds`)보다 짧아야 한다.
