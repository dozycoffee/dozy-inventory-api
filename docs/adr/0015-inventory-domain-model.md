# ADR-0015: 재고 도메인 모델 규칙

## 상태

Accepted (2026-10-07)

## 배경 (Context)

F-007에서 `lot`, `inventory`, `inventory_history` 도메인 모델을 만든다. 예약·출고 같은 수량 변경은 읽고-계산하고-쓰기가 아니라 DB의 조건부 UPDATE로 처리하므로([ADR-0003](0003-reservation-concurrency-conditional-update.md)), 도메인 모델이 무엇을 맡는지 정해야 한다.
계층별로 PR을 나눠 진행하며 F-007은 도메인과 영속성 어댑터까지만 만들고 UseCase·API는 F-008(입고 확정)·F-009(조회)에서 만든다.

## 결정 (Decision)

1. **도메인 모델은 수량 규칙과 실패 원인을 표현하고, 동시 요청의 최종 판정은 DB가 한다.** `Inventory`는 총 수량 ≥ 0, 0 ≤ 예약 수량 ≤ 총 수량, 할당 보류이면 보류 시각 존재를 지킨다. 영속성 어댑터의 조건부 UPDATE와 같은 규칙인지는 실제 MySQL로 검증한다. UPDATE가 0건이면 행을 다시 조회해 `checkReservable`로 원인(품질 상태, 보류, 수량 부족)을 판별한다.
2. **`Inventory`의 연산은 `increase`(입고·반품·조정 증가), `decrease`(폐기·조정 감소), `reserve`, `release`, `ship`(출고 확정), `hold`/`releaseHold`(할당 보류)이다.** 품질 상태 전환은 두 행의 감소와 증가의 조합이라 application에서 구성한다. 수량이 0이 되어도 행은 유지한다(삭제 연산이 없다).
3. **감소(`decrease`)는 가용 수량 안에서만 가능하다.** 예약된 수량은 줄일 수 없다. 예약 해제는 품질 상태·보류와 무관하게 가능하고, 예약은 정상 품질이고 보류가 아닌 행만 가능하다. 예약 불가 원인의 판별 순서는 품질 상태 → 보류 → 수량 부족이다.
4. **`Lot`의 상태는 기준일과 임박 기준 일수를 인자로 받아 판정한다.** 유통기한이 기준일 이하이면 `EXPIRED`, 기준일 + N일 이내이면 `EXPIRING_SOON`, 유통기한이 없으면 항상 `NORMAL`이다. N(30일)은 유통기한 스캔(F-017)에서 설정으로 두고 넘긴다. Lot 번호는 공급사 값 그대로 보존한다(공백·대소문자 변환 없음, ERD-08).
5. **`InventoryHistory`는 변경할 수 없는 값이다.** 변동량은 0일 수 없고, 입고·반품은 증가, 출고·폐기는 감소여야 하며, 변경 후 수량은 0 이상이다. 생성 시각은 읽기 전용 값으로만 가진다.
6. **멱등 키는 값 객체 `IdempotencyKey`로 검증한다.** 공백 없는 ASCII 출력 문자(0x21~0x7E) 최대 100자, 대소문자를 구분한다(ERD-07).
7. **입고 upsert는 `INSERT ... ON DUPLICATE KEY UPDATE`로 한 문장에 처리한다**(영속성 어댑터에서 구현).

## 결과 (Consequences)

- 얻는 것: 수량 불변식과 실패 원인이 한 곳에 모이고, 단위 테스트로 경계값을 검증할 수 있다. 동시성은 DB가 보장한다.
- 감수하는 것: 같은 규칙이 모델(Kotlin)과 SQL(조건부 UPDATE, CHECK)에 두 번 있어 어긋날 수 있다. 그래서 둘의 일치를 검증하는 테스트를 영속성 어댑터에 둔다.
