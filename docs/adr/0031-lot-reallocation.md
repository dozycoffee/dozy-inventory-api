# ADR-0031: Lot 재할당과 할당 보류 규칙

## 상태

Accepted (2026-10-12). 시나리오 6.2 원문이 Notion에만 있어 아래 결정은 사용자 확인(대체 Lot 선택 주체, 요청 단위, 실패 시 보류, 이벤트 발행)을 거쳤고, 멱등 처리와 나머지는 ADR-0022·0024의 선례를 따랐다. 구현은 계층별 PR로 나눈다: (1) inventory의 할당 보류 UseCase와 reservation 도메인·영속성, (2) 재할당 application, (3) 웹 어댑터.

## 배경 (Context)

예약이 확정(`CONFIRMED`)되면 WMS가 Lot별 수량으로 피킹한다(ADR-0023). 현장에서 지정된 Lot을 피킹할 수 없는 경우(파손, 위치 불명, 실물 부족)가 생기며, 이때 WMS가 inventory 서비스에 재할당을 요청한다(시나리오 결정 1, 11). 부족이 보고된 Lot 행에 다른 예약이 계속 할당되면 같은 문제가 반복되므로 그 행은 신규 할당에서 제외(보류)하고, 보류는 실사 조정(ADR-0026)이나 대사 보정으로 실물이 정리되면 자동으로 풀린다.

## 결정 (Decision)

1. **재할당은 확정(`CONFIRMED`) 예약에만 한다.** 확정 전·해제·만료·출고 완료된 예약은 409(`INV_INVALID_RESERVATION_STATE`)이다. 확정 전 예약은 해제하고 다시 예약하면 된다.
2. **요청 단위는 예약 하나와 재고 행별 부족 수량이다**(사용자 확인). `POST /api/v1/reservations/{id}/reallocation`, 본문은 `shortages[{inventoryId, shortageQuantity}]`이다. 재고 행은 그 예약에 할당된 행이어야 하고 같은 행을 두 번 담을 수 없으며 부족 수량은 1 이상 그 행의 할당 수량 이하여야 한다(어기면 400 `INV_INVALID_REALLOCATION`). 부족 수량만 다른 Lot으로 옮기고 나머지 할당은 그대로 둔다.
3. **대체 Lot은 inventory가 자동으로 고른다**(사용자 확인). 예약 생성과 같은 FEFO 규칙(ADR-0022 결정 4)을 같은 창고·같은 상품 안에서 쓴다. 부족이 보고된 행은 보류되어 후보에서 빠진다. 재할당된 수량이 같은 예약 항목에 이미 할당된 다른 Lot과 겹치면 그 할당의 수량이 늘어난다. 할당 수량이 0이 된 행은 할당에서 지운다(`reservation_allocation`의 0 허용은 안전망으로 남겨 둔다).
4. **부족이 보고된 행은 먼저 할당 보류로 확정하고, 재할당은 그 뒤 별도 트랜잭션으로 한다**(사용자 확인). 부족 보고는 실물에 대한 사실이라 대체 재고가 모자라 재할당이 실패(409 `INV_INSUFFICIENT_AVAILABLE_QUANTITY`)해도 보류는 남는다. 보류 사유는 `피킹 불가 보고: 예약 {id}`이고 이미 보류 중인 행은 처음의 사유·시각을 유지한다. 입력이 잘못된 요청(결정 1, 2 위반)은 보류하기 전에 거부한다.
5. **재할당 트랜잭션**: 예약 행을 조건부 UPDATE로 잠근 뒤(상태 `CONFIRMED` 유지) 대체 Lot의 예약 수량을 잡고(`allocate`), 부족이 보고된 행의 예약 수량을 되돌린다(`release`). 총 수량은 건드리지 않는다. 실물이 모자란 것이라 원인은 실사 조정(F-015)과 대사(F-019)로 정리한다(결품과 같은 원칙, ADR-0024). 예약 할당 저장, `REALLOCATED` 이력, 이벤트, 수량 변경은 한 트랜잭션이다. 잠금 순서는 예약 행 → 재고 행이다. 다른 요청에 밀리면 트랜잭션을 새로 열어 다시 시도한다(최대 5회).
6. **총 수량이 바뀌지 않으므로 `inventory_history`는 남기지 않는다.** 대신 `reservation_event`(`REALLOCATED`)에 부족 내역과 새 할당을 남긴다.
7. **멱등 키는 `Idempotency-Key` 헤더이고 `reservation_event.idempotency_key`가 유니크 `(reservation_id, idempotency_key)`로 중복을 막는다**(재할당은 `inventory_history`를 남기지 않아 이 이력이 처리 기준이다). 같은 키의 재요청은 부족 내역이 같으면 새로 반영하지 않고 처음 요청이 만든 할당(이력에 기록)에 현재 Lot 정보를 붙여 처음과 같은 응답을 주고, 내용이 다르면 409(`INV_IDEMPOTENCY_KEY_CONFLICT`)이다. 동시에 같은 키가 오면 한쪽의 이력 저장이 유니크 위반으로 롤백되거나 재고 행을 건드리기 전 할당 확인(결정 5)에서 밀려 다시 시도하고, 다시 읽으면 저장된 이력이 있어 같은 결과를 반환한다. 트랜잭션 밖의 사전 확인은 이력을 먼저 읽고 예약을 나중에 읽으며, 검증이 실패했을 때는 이력을 한 번 더 확인해 방금 끝난 같은 키의 요청을 입력 오류로 오인하지 않는다.
8. **응답은 재할당 뒤의 예약 전체 할당이다**: 예약 ID, 상태, 새로 보류된 재고 행 ID, 상품별로 재고 행·Lot ID·Lot 번호·유통기한·수량. WMS는 이 목록으로 피킹 지시를 바꾼다.
9. **이벤트는 `RESERVATION_REALLOCATED`를 발행한다**(사용자 확인). 기존 예약 이벤트와 같은 토픽·키·본문 모양이며 `allocations`는 재할당 뒤 상태이다(할당 수량 0인 행 없음). `docs/events.md`의 예약 이벤트 계약에 추가한다.
10. **보류 해제는 ADR-0026이 이미 한다**(실사 조정이 반영한 행의 보류 해제). 대사 보정(F-019)이 같은 규칙을 쓴다. 보류 상태는 관리자 재고 현황(ADR-0030)에서 `allocationHold`로 조회한다.
11. **호출은 `inventory:service`만 허용한다**(WMS는 system client).
12. **API 오류**: 입력 불일치 400(`INV_INVALID_REALLOCATION`), 예약 없음 404, 불가능한 상태 409(`INV_INVALID_RESERVATION_STATE`), 대체 재고 부족 409(`INV_INSUFFICIENT_AVAILABLE_QUANTITY`), 다른 내용의 같은 키 409(`INV_IDEMPOTENCY_KEY_CONFLICT`), 계속 겹침 409(`INV_RESERVATION_CHANGED_CONCURRENTLY` 또는 `INV_ALLOCATION_CONFLICT`).

## 결과 (Consequences)

- 얻는 것: 피킹 불가 Lot의 수량이 예약을 깨지 않고 다른 Lot으로 옮겨지고, 같은 Lot이 다른 예약에 계속 할당되지 않으며, 대체 재고가 없어도 부족 사실은 남는다.
- 감수하는 것: 재할당이 실패하면 호출한 쪽이 보류만 된 상태로 응답을 받는다(재고를 보충한 뒤 새 멱등 키로 다시 요청한다). 총 수량이 실물보다 많은 상태는 실사 조정 전까지 이어진다. 보류의 이력 테이블이 없어 지난 보류는 `REALLOCATED` 이력으로만 추적한다(ERD-04).
