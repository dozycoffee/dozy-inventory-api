# ADR-0017: 입고 확정 반영 규칙

## 상태

Accepted (2026-10-07)

## 배경 (Context)

F-008에서 WMS의 입고 확정을 재고에 반영한다. 시나리오 3.1이 요청 내용, Lot 등록, 멱등, 반려 조건을 정했고, 요청 단위·Lot 불일치·비활성 상품·이벤트·트랜잭션 경계·API 형태가 남았다. 계층별로 PR을 나누며 이 결정은 application 계층(UseCase, 서비스)부터 적용하고 웹 어댑터는 다음 PR에서 만든다.

## 결정 (Decision)

1. **요청 한 건은 입고 품목 한 줄이다.** 멱등 키는 품목마다 하나이고 원인 문서 ID(입고 상품 ID)도 하나라 이력 한 행과 1:1이다. 같은 입고에 같은 (상품, Lot, 품질) 행이 여러 줄이어도 각각 독립 요청이다. 부분 실패는 요청별로 재시도한다.
2. **기존 Lot과 제조일자·유통기한이 다르면 `IMS_LOT_MISMATCH`(409)로 거부한다.** 같은 Lot에 서로 다른 유통기한이 섞이는 조용한 오류를 막는다(ERD-08과 같은 이유). 한쪽이 없는 것과 있는 것도 다르다.
3. **상품이 있으면 `INACTIVE`도 입고를 반영한다.** 이미 도착해 WMS가 확정한 물건이므로 장부에 반영해야 한다(원칙 7). 품질 상태는 WMS 검수 판정인 `NORMAL`·`DEFECTIVE`만 받고 `DISPOSAL_SCHEDULED`는 400이다(폐기 예정은 유통기한 스캔이 정한다).
4. **`재고 증가` 이벤트는 출력 포트(`InventoryEventPublisher`)와 이벤트(`InventoryEvent`)를 정의하고 로그만 남기는 구현을 둔다.** Outbox 저장 구현은 F-018에서 교체한다. 상품 이벤트와 같은 방식이다.
5. **서비스는 트랜잭션 밖에서 오케스트레이션하고 안쪽만 `TransactionalOperator`로 감싼다.** 수량·이력·이벤트는 한 트랜잭션이다. 같은 멱등 키가 동시에 들어오면 늦은 쪽의 이력 저장이 중복 키로 실패해 롤백되고(수량 갱신도 되돌아간다), 서비스가 트랜잭션 밖에서 저장된 이력으로 이전 결과를 반환한다. 같은 Lot이 동시에 처음 들어오면 늦은 쪽의 Lot 저장이 중복으로 실패하므로 한 번 다시 시도한다(MySQL REPEATABLE READ에서는 같은 트랜잭션 안에서 다시 조회해도 방금 커밋된 Lot이 보이지 않아 새 트랜잭션이 필요하다).
6. **재요청은 처음 응답과 같은 결과를 반환한다.** 이력의 `quantity_after`(처음 시점의 총 수량)로 결과를 다시 만들고, 저장된 이력의 내용(창고, 상품, 품질 상태, Lot 번호, 수량, 원인 문서)과 요청을 비교해 다르면 거부한다.
7. **Lot의 임박 기준 일수는 설정 `ims.inventory.expiring-soon-days`(기본 30)로 둔다.** 새 Lot을 등록할 때 `Clock`의 오늘을 기준으로 초기 상태를 정한다. 유통기한 스캔(F-017)도 같은 설정을 쓴다.
8. **API는 `POST /api/v1/inbound-receipts`이고 호출은 `ims:service`만 허용한다**(웹 어댑터 PR에서 구현). 수량은 WMS 확정으로만 바뀌므로(원칙 6) 본사 관리자(`ims:admin`)도 직접 입고를 넣을 수 없다.

## 결과 (Consequences)

- 얻는 것: WMS 재전송에 안전하고(멱등), 동시 요청에서도 수량이 정확하며(실제 MySQL 50개 동시 테스트), 데이터 불일치(Lot 날짜, 같은 키 다른 내용)를 조용히 넘기지 않는다.
- 감수하는 것: 입고가 품목 단위 호출이라 한 입고에 품목이 많으면 호출 수가 늘고 입고 전체가 원자적이지 않다. 서비스에 트랜잭션 오케스트레이션 코드가 들어간다. 이벤트는 Outbox 구현 전까지 실제로 발행되지 않는다. 같은 Lot의 첫 동시 입고 중 늦은 요청은 한 번 더 시도하느라 조금 느리다.
