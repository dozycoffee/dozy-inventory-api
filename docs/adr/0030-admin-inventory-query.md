# ADR-0030: 관리자 재고 현황·상세·이력 조회 규칙

## 상태

Accepted (2026-10-14). 채널용 가용 재고 조회(ADR-0020)에 이어 F-009의 2단계이고, 시나리오 4장 원문이 Notion에만 있어 사용자 확인을 거친 항목 외에는 ADR-0020과 기존 API의 선례를 따랐다.

## 배경 (Context)

본사 관리자가 재고를 살펴보고 문제를 추적하려면 재고 현황, 재고 행 하나의 상세, 그 행의 수량 변동 이력을 볼 수 있어야 한다. 채널용 조회(ADR-0020)는 가용 수량만 주고 Lot·유통기한을 노출하지 않으며 전체 목록은 이 관리자 조회가 맡는다고 정했다.

## 결정 (Decision)

1. **현황의 한 줄은 재고 행(창고 × Lot × 품질 상태)이다**(사용자 확인). 총 수량·예약 수량·가용 수량(총 − 예약, 행 자체의 값이며 품질 상태·보류는 반영하지 않는다), 품질 상태, 할당 보류와 사유·시각, Lot 번호·제조일자·유통기한·Lot 상태, 생성·변경 시각을 한 줄에 준다. 수량 변동이 모두 이 행 단위라 이력과 바로 이어진다.
2. **상품 이름 같은 product 정보는 응답에 넣지 않고 `productId`만 준다.** 다른 도메인의 테이블을 JOIN하지 않는다(ADR-0010). 필요하면 호출한 쪽이 상품 조회로 채운다.
3. **조회 조건은 모두 선택이다**: `warehouseId`, `productId`, `qualityStatus`, `lotStatus`, `allocationHold`. 주어진 조건을 모두 만족하는 행을 주고, 조건 없이 부르면 전체를 준다(ADR-0020 결정 4가 이 조회에 맡긴 전체 목록). 정렬은 `창고, 상품, 유통기한(없는 Lot은 마지막), 재고 행 ID`이고 정렬 지정은 받지 않는다.
4. **페이지는 `page`(0부터, 기본 0)와 `size`(1~100, 기본 20)이고 응답에 `totalElements`와 `totalPages`를 담는다.** 범위를 벗어나거나 ID가 양수가 아니면 400(`INV_INVALID_INVENTORY_QUERY`), 알 수 없는 품질·Lot 상태 값은 `VALIDATION_FAILED`다.
5. **상세는 재고 행 하나(현황과 같은 필드)이고 없으면 404(`INV_INVENTORY_NOT_FOUND`)다.**
6. **이력은 재고 행의 `inventory_history`를 최신순(생성 시각, ID 내림차순)으로 페이지로 준다.** 유형, 변동량, 변경 후 총 수량, 원인 문서 유형·ID, 멱등 키, 요청 주체, 생성 시각을 담고 재고 행이 없으면 404다. `(inventory_id, created_at)` 인덱스를 쓰므로 새 마이그레이션이 없다.
7. **경로와 권한**: `GET /api/v1/inventories`(현황), `GET /api/v1/inventories/{inventoryId}`(상세), `GET /api/v1/inventories/{inventoryId}/histories`(이력). 모두 `inventory:admin`만 호출한다. 창고 관리자는 배정된 창고만 볼 수 있어야 하므로 창고 접근 제어(F-021) 이후에 연다(ADR-0032에서 창고 관리자에게 현황·상세·이력과 가용 재고 조회를 열었다).
8. **읽기 전용이라 락을 걸지 않고 조회 결과는 약속이 아니다**(원칙 3). 약속은 예약으로만 한다.

## 결과 (Consequences)

- 얻는 것: 관리자가 재고 행을 필터로 찾고 Lot·보류·예약을 확인하며 변동 이력을 추적할 수 있다. 채널용 조회와 목적이 분리된다.
- 감수하는 것: 행 단위 목록이라 상품 단위로 합친 현황이 필요하면 따로 집계를 만들어야 한다. 상품 이름이 없어 화면이 상품 조회를 추가로 불러야 한다. 큰 `page` 값은 OFFSET 비용이 커진다(관리자 조회라 허용).
